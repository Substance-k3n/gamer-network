# Data model

The Postgres schema for the MVP (ADR-0001). Status: **proposed**, to be
built in BUILD_PLAN phase 1 with Drizzle (ADR-0006). When the migrations
exist they are the source of truth; update this file in the same PR as
any migration.

Visual version (diagram + screen map):
https://claude.ai/artifact/DFPiu8i5D2guzr9LgE9RHq (private; share it from its menu).

## Conventions

- Postgres 17. Extensions: `citext`.
- IDs are `uuid`, generated by the API as UUIDv7 (time-ordered, so
  `ORDER BY id` is creation order and cursors are cheap). Catalog tables
  (`games`) use readable text slugs instead.
- Every time is `timestamptz`, stored in UTC. The launch city is in
  `Africa/Addis_Ababa` (UTC+3, no daylight saving); "tonight" and the
  next-day check-in are computed in that zone.
- Enums are Postgres enums. Adding a value is a migration; removing one
  is a new ADR.
- Soft delete only for `users` (Play requires account deletion; we keep
  the row so references hold and scrub its personal data after 30 days).
  Everything else is deleted or moves to a terminal status.
- Table and column names are `snake_case`; the API speaks `camelCase`.

## Tables

### Identity and sign-in

**`users`**: one row per gamer. The profile header, the onboarding step 1
form, the status card.

| Column                     | Type              | Notes                                                                |
| -------------------------- | ----------------- | -------------------------------------------------------------------- |
| `id`                       | uuid PK           |                                                                      |
| `email`                    | citext unique     | Never shown to other users                                           |
| `email_verified_at`        | timestamptz null  | Set by the verification code, a password reset, or Google sign-in    |
| `password_hash`            | text null         | argon2id. Null for Google-only accounts (ADR-0007)                   |
| `username`                 | citext unique     | `^[a-z0-9._]{3,20}$`, e.g. `kaleb.gg`                                |
| `display_name`             | text              | 1–30 chars                                                           |
| `bio`                      | text null         | ≤ 160 chars                                                          |
| `avatar_key`               | text null         | Object key in R2; the API returns a URL                              |
| `age_range`                | age_range         | 16+ only (ADR-0005). No birth date stored                            |
| `country`                  | char(2)           | Default `ET`                                                         |
| `city`                     | text              | Default `Addis Ababa`; free text later, a fixed list for launch      |
| `status`                   | player_status     | Default `not_available`                                              |
| `status_game_id`           | text null → games | For "Playing Valorant"                                               |
| `status_until`             | timestamptz null  | `available_tonight` and `playing` clear themselves at this time      |
| `available_days`           | smallint          | Bitmask Mon=1 … Sun=64 (the MO–SU row on the status card). Default 0 |
| `role`                     | user_role         | Default `player`                                                     |
| `onboarded_at`             | timestamptz null  | Set by "Go live". Users without it don't appear anywhere             |
| `banned_at`                | timestamptz null  | Banned users can't sign in; their listings are removed               |
| `created_at`, `updated_at` | timestamptz       |                                                                      |
| `deleted_at`               | timestamptz null  | Account deletion. Personal fields scrubbed 30 days later by a job    |

**`auth_identities`**: linked outside sign-ins. `(provider, subject)`
unique. For now only `provider = google` (subject = Google `sub`).
Email + password lives on `users` itself (ADR-0007). One user can have
both.

**`email_codes`**: 6-digit codes for verifying an email and resetting a
password. `email`, `purpose` email_code_purpose, `code_hash` (never the
code), `expires_at` (10 min), `attempts` (max 5), `consumed_at`. Max 5 sent
per email per hour.

**`sessions`**: `user_id`, `token_hash` (sha-256 of an opaque random
token; unique), `created_at`, `last_seen_at`, `expires_at` (90 days,
sliding), `user_agent`, `revoked_at`.

**`devices`**: push targets. `user_id`, `fcm_token` (unique), `platform`
(`android`|`ios`|`web`), `app_version`, `last_seen_at`. A token that FCM
reports as invalid is deleted.

### Game catalog (seeded, not user-made)

**`games`**: `id` text PK, the same short ids the app uses (`val`,
`codm`, `pubg`, `fc`, …), `name`, `short_code` (`VAL`, the tile label),
`platforms` platform[], `has_ranks` boolean (false = the ladder is
skill or play-style levels, as in Minecraft),
`max_party` smallint (5 for Valorant, 4 for PUBG squads),
`is_launch` boolean (the 2–3 launch games appear in Find Players filters),
`sort` smallint. Seeded from the app's catalog in
`apps/mobile/lib/data.dart` (49 games with their rank ladders).

**`game_ranks`**: `id` uuid, `game_id`, `name` (`Diamond`, `Div 3`,
`Legendary`), `tier` smallint (order, low → high). Unique `(game_id, tier)`
and `(game_id, id)` so other tables can reference a rank _of that game_.

**`game_roles`**: `id`, `game_id`, `name` (`Duelist`, `Slayer`, `Jungle`).

**`game_modes`**: `id`, `game_id`, `name` (`Ranked`, `Unrated`, `Battle
Royale`), `is_ranked` boolean.

### Gamer profile

**`user_games`**: `id` uuid PK, `user_id`, `game_id` null,
`custom_game_name` null (≤ 40; a game not in the catalog, which the app
lets you add by name; exactly one of the two is set), `rank_id` null,
`rank_text` null (≤ 30, free text for custom games), `role_id` null,
`position` smallint (order on the profile). Unique `(user_id, game_id)`
and `(user_id, lower(custom_game_name))`. Custom games show on profiles
but can't have listings. Composite FKs
`(game_id, rank_id) → game_ranks(game_id, id)` and the same for roles, so a
Valorant row can't hold an FC rank. Ranks are self-reported (ADR-0005);
the app says so ("Self-reported" on the Games tab).

**`user_platforms`**: PK `(user_id, platform)`.

**`user_tags`**: PK `(user_id, tag)`. Max 6 per user.

**`gaming_ids`**: `id`, `user_id`, `kind` gaming_id_kind, `game_id` null
(required when `kind = in_game`, e.g. a PUBG Mobile UID), `value` text
(≤ 64), `visibility` id_visibility default **`connections`**.
Unique `(user_id, kind, game_id)`.

### Find Players

**`listings`**: a "Looking for players" post. Short-lived.

| Column                    | Type           | Notes                                                                                |
| ------------------------- | -------------- | ------------------------------------------------------------------------------------ |
| `id`                      | uuid PK        |                                                                                      |
| `owner_id`                | uuid → users   |                                                                                      |
| `game_id`                 | text → games   | Must be a launch game                                                                |
| `mode_id`                 | uuid null      | FK `(game_id, mode_id)`                                                              |
| `rank_id`                 | uuid null      | The rank this group plays at; FK `(game_id, rank_id)`. Defaults to the owner's       |
| `platform`                | platform       |                                                                                      |
| `party_size`              | smallint       | Whole party incl. owner: 2 = Duo, 3 = Trio, 4 = Squad, 5 = Five. ≤ `games.max_party` |
| `filled`                  | smallint       | Accepted players so far (owner not counted). `filled = party_size - 1` → `full`      |
| `voice`                   | voice          | `required` = "Mic required", or `optional`                                           |
| `style`                   | play_style     |                                                                                      |
| `play_when`               | play_when      |                                                                                      |
| `starts_at`               | timestamptz    | Worked out by the API from `play_when`; see expiry rules                             |
| `duration_hours`          | smallint       | What the poster picked: 2, 6 or 24 ("Expires after")                                 |
| `expires_at`              | timestamptz    | `created_at + duration_hours`                                                        |
| `note`                    | text null      | ≤ 140 chars                                                                          |
| `city`                    | text           | Copied from the owner at creation, for filtering                                     |
| `status`                  | listing_status | Default `open`                                                                       |
| `created_at`, `closed_at` | timestamptz    |                                                                                      |

Indexes: partial unique `(owner_id) WHERE status IN ('open','full')` —
**one live listing per person**; `(city, game_id, expires_at) WHERE
status = 'open'` for the feed.

### Relationships

**`connection_requests`**: "Connect" on a listing card or a profile.
`id`, `from_user_id`, `to_user_id` (check: different), `listing_id` null
(set when sent from a listing; that's what "Hana wants to play · Div 2 EA
FC 25" shows), `message` null (≤ 140), `status` request_status,
`created_at`, `responded_at`. Partial unique `(from_user_id, to_user_id)
WHERE status = 'pending'`.

**`connections`**: PK `(user_a_id, user_b_id)` with check
`user_a_id < user_b_id` so each pair is stored once. `created_at`,
`source_request_id` null, `source_listing_id` null. Removing a
connection deletes the row.

**`play_invites`**: the "Play together" button between connections.
`id`, `from_user_id`, `to_user_id`, `game_id`, `play_when` invite_when,
`starts_at` (now, now + 30 min, or 21:00 local tonight), `status`
invite_status, `created_at`, `expires_at` (`starts_at` + 15 min: an
invite nobody answered by then is stale), `responded_at`.

**`check_ins`**: the metric (PRD). `id`, `user_id` (who is asked),
`other_user_id`, `listing_id` null, `play_invite_id` null, `due_at`,
`answer` check_in_answer null, `answered_at`, `created_at`.
Unique `(user_id, other_user_id, listing_id)` and
`(user_id, play_invite_id)`.

### Notifications

**`notifications`**: the Alerts list. `id`, `user_id`, `type`,
`actor_id` null, `listing_id` / `connection_request_id` /
`play_invite_id` / `check_in_id` null, `read_at` null, `created_at`.
Index `(user_id, id DESC)`. A push is sent for each row unless the user
muted that type (later).

### Safety and admin

**`blocks`**: PK `(blocker_id, blocked_id)`, `created_at`.

**`reports`**: `id`, `reporter_id`, `target_user_id` (always set),
`listing_id` null, `reason` report_reason, `details` null (≤ 500),
`status` report_status default `open`, `created_at`, `resolved_by` null,
`resolved_at` null, `resolution_note` null.

**`admin_actions`**: audit log. `id`, `admin_id`, `kind`
admin_action_kind, `target_user_id` null, `listing_id` null,
`report_id` null, `note`, `created_at`. Every admin endpoint writes one.

### Growth

**`waitlist`**: PK `(user_id, topic)`, `created_at`. `topic` is `groups`
for the Groups "Notify me" button; free text so we can test other ideas.

## Rules the schema alone can't hold

These live in the services and each has a test.

**Listing times.** The app sends `playWhen` and `durationHours`; the API
works out the rest, in Addis time. `starts_at`: `now` → created time;
`tonight` → 20:00 today, or the created time if later; `weekend` → 10:00
the coming Saturday, or the created time if it is already the weekend.
`expires_at` = created + 2, 6 or 24 h, whatever the poster picked. A
`weekend` listing posted on Monday with 24 h would expire before it
starts, so `weekend` listings get at least until `starts_at` + 6 h. A job every minute sets
`status = 'expired'` on passed listings and `expired` on their pending
requests; reads also filter on `expires_at > now()` so a late job never
shows a dead listing. 15 min before expiry the owner gets
`listing_expiring`.

**Listing lifecycle.** `open` → `full` (filled reached) → back to `open`
if someone leaves; `open|full` → `closed` (owner), `expired` (time),
`removed` (admin). Terminal states never reopen; post a new one.

**Accepting a request from a listing.** In one transaction: request →
`accepted`, insert `connections` (if not already connected), `filled + 1`
and `full` if reached, notify the requester, and create two `check_ins`
(one for each person) due **12:00 local the next day**.

**Accepting a play invite.** Creates the same pair of check-ins for that
invite, due 12:00 local the next day (or in 6 h if accepted before 06:00).

**Passwords and accounts.** Passwords are 8–72 characters, hashed with
argon2id. Sign-in failures say "Wrong email or password" whichever part
was wrong; 10 failures in 15 min lock that email for 15 min. Sign-up
sends a `verify_email` code; the account works before it is verified,
but listings and requests need a verified email. "Forgot password"
sends a `reset_password` code; using it sets the new password, verifies
the email and revokes all other sessions. Google sign-in with an email
that already has a password account links to it; if that account was
never verified, its password is cleared, so whoever created it without
owning the email loses access.

**Gaming ID visibility.** `public` IDs show to everyone signed in.
`connections` IDs show only to connected users (and the owner). Never in
the public share page.

**Blocks.** If either person blocked the other: profiles return 404 to
each other, listings are hidden both ways, requests and invites are
refused, an existing connection is deleted, pending requests between
them are cancelled.

**Banned or deleted users** are excluded everywhere (listings, search,
counts) and their sessions are revoked.

**"Looking now" counter.** Distinct users in the city with an open
listing or `status = 'looking'` set in the last 12 h.

**Profile stats.** Connections = connection rows. Games = `user_games`
rows. **Played with** = distinct `other_user_id` with a `played` check-in.

**The metric.** For listings created in a period: share with at least one
`check_ins.answer = 'played'` row pointing at them. `GET
/v1/admin/metrics` returns it.

**Limits.** One live listing per user. 30 connection requests and 20 play
invites per user per day. Re-requesting someone who declined you waits 7
days.

## Not in the MVP

Posts, comments, reactions, clips ("Game Moments"), groups, game pages,
chat, rank verification. The Home feed and the profile's Posts/Moments
tabs in the prototype are not built (ADR-0001). When they come, they get
their own tables and an ADR; nothing here needs to change for them.
